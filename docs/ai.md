# AI 能力说明

> 这一层不是"接个聊天框"，而是**把 AI 放到具体动作上**：查数、判断、生成、执行、被校准。
> 所有调用都走服务端，Key 不下发浏览器；所有有副作用的动作都要人确认。

---

## 一、整体结构

```
用户（网页对话框 / 钉钉群 @机器人）
        │
        ▼
  意图路由  ── 明确的固定句式 → 内置指令引擎（不耗 token，毫秒级）
        │
        └─ 开放式问题 → 大模型（OpenAI 兼容）
                            │
                            ├─ 工具调用（17 个，最多 3 轮）
                            │    查：审批/待办/等待回复/日程/资料/统计
                            │    做：建任务/建日程/完成任务/发钉钉/发邮件/提审批
                            │    产：周报聚合/联网搜索/读网页/天气
                            ▼
                       基于真实数据回答
```

两条硬规矩写在系统提示词里：**涉及工作台数据必须先用工具查询再回答、禁止编造**；**外部信息必须联网搜索而不是凭记忆**。

典型链路（实测 1~6 秒）：

- 「今天有什么安排」→ `overview` + `query_schedule` + `query_todo` → 合成三段
- 「新建任务 核对报价单 高优先级 明天」→ `create_task` → 返回新建结果
- 「这周干了什么，写份周报」→ `work_report` → 按五板块成稿（任务/审批/日程/群消息/待跟进）
- 「这单能不能批」（在审批卡片上）→ `approval_agent.judge`（见下）

## 三、审批判断 Agent

### 3.1 一次完整的活

| 步 | 做什么 | 实现 |
|---|---|---|
| 1 读单 | 取表单正文（事由/金额/时间/附件）+ 流转记录（谁批过、同意还是拒绝、几点） | `approval_agent.load_case` |
| 2 比对 | 近 **90 天** 同类型已结论单据，最多 **12 条**样本；加制度文本 | `similar_history` + `ai:policy` |
| 3 判断 | 四选一：通过 / 退回 / 需补材料 / 建议人工，附依据、风险、缺失项 | 大模型结构化输出（JSON） |
| 4 出意见 | 生成可直接粘贴进审批意见的话 | 同上 `comment` 字段 |
| 5 校准 | 记录"判断对/有误"，算一致率 | `judge_log` + `/api/judge/stats` |

### 3.2 护栏（写死在代码里）

| 护栏 | 触发条件 | 结果 |
|---|---|---|
| 无正文不下结论 | 库里没有 `表单明细` | 返回 `need_info`，**不调模型**，提示先补正文 |
| 无依据不猜 | 既无制度、又无历史样本 | 返回 `manual`（建议人工），不编 |
| 大额降置信 | 金额 ≥ 5000 | 置信度强制下调，追加"建议复核" |
| 结论白名单 | 模型输出越界 | 归一到四种之一，不产生第五种 |
| 不自动提交 | 任何情况 | 只出建议，提交动作由人点 |
| 缓存 | 同一单 1 小时内 | 直接返回上次结果（`force` 可跳过） |

### 3.3 口径：制度 + 历史双轨

- **制度**：`ai:policy` 里的文本条款，优先级最高。
- **历史**：你过去 90 天对同类型单的实际批法，用来说明"你通常会怎么批"。
- **冲突**：两者矛盾时，`conflict` 字段显式写出"制度说不行，但你上次批了"，把价值判断留给人。

配置方法见 [config.md#42-审批判断的制度口径](config.md)。

### 3.4 反馈闭环

面板底部有「判断对 / 判断有误」，写入 `judge_log.adopted`。

```bash
curl -s "$HOST/api/judge/stats?days=30&token=$TOKEN"
# {"total":42,"feedback":30,"adopted":27,"agreement":90,"by_verdict":{"approve":25,"return":12,"need_info":5},"days":30}
```

**准入规则**：盲评 30 张单，一致率 < 80% 不放开任何自动化；≥ 80% 才考虑"小额单自动批"这类更高权限。
这条规则写在文档里，也建议写进你们的内部流程。

### 3.5 评测怎么做（建议流程）

1. 挑 30 张**已结案**的历史单（覆盖补卡/加班/请假/采购/付款/离职），先不看原结论。
2. 逐张点「AI 判断」，把结论记下来。
3. 对照真实结论，算一致率；把"AI 对但人错"和"人批得随意"的单单独标记。
4. 一致率 < 80% → 先补制度文本、补历史正文（`backfill_form.py`），再测。
5. ≥ 80% → 在部门内试用，仍只出建议。

## 四、模型怎么选、花多少钱

| 场景 | 建议模型档位 | 说明 |
|---|---|---|
| 审批判断 | 中高档（推理稳） | 单次约 6k~10k 输入 token（含 12 条历史），输出 500 token 内 |
| 周报生成 | 中档 | 一次 3k~8k token |
| 日常问答 | 低档足够 | 工具调用对模型要求不高 |

成本粗略量级（按 1 元/百万输入 token 档位）：审批判断单次约 0.01 元，一个人一天 10 单约 0.1 元。
**注意**：判断是"点一次算一次"，有 1 小时缓存，不做全量预跑。

配置见 [config.md#四ai-模型与制度](config.md)。任意 OpenAI 兼容网关都行，包括本地 Ollama。

## 五、钉钉机器人

| 项 | 值 |
|---|---|
| 回调地址 | `http://你的地址:8787/dingtalk/robot` |
| 接收模式 | HTTP 推送（明文 JSON + `timestamp`/`sign` 头） |
| 验签 | `base64(HMAC-SHA256(timestamp, AppSecret))`，与平台配置里的 AppSecret 一致 |
| 落库 | 命中「等待回复」，群里 @机器人 不刷屏回复 |
| 只收 @我 | 平台配置 `robot_only_at_me=1` |

拿不到历史群聊：钉钉不开放群聊天记录读取，所以群消息只覆盖"机器人上线后 @ 到它的消息"。
这一条是平台限制，不是实现缺陷。

## 六、AI 不做什么

| 不做 | 原因 |
|---|---|
| 自动批审批 | 出错要担责且无法解释；只出建议 |
| 自动发消息给外部 | 有副作用，必须人确认 |
| 猜数据 | 查不到就说查不到，不做补全 |
| 绕过权限 | 工具全部走 `person_id` 过滤，管理员视角才看全量 |
| 读取群历史 | 平台未开放 |

## 七、怎么扩展

加一个新工具（例：`query_calendar_conflicts`）：

1. `ai_bot.py` → `LLM_TOOLS` 里加一条 JSON Schema（`name` / `description` / `parameters`）。
2. `ai_bot.py` → `_tool_exec` 里加分支，返回 `{'ok':True,'data':...}` 或 `{'ok':False,'error':'缺什么'}`。
3. 系统提示词里加一句"用户问 X 时用该工具"。
4. `docker compose up -d --build`。

换一套判断口径（例：按部门差异化）：在 `approval_agent.py` 的 `judge()` 里按 `审批类型` 拼不同 `policy` 片段即可。
